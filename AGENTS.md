# Gramin Kirana — AI Operational Rules

You are operating within a constrained compute environment. To optimize resource usage, prevent quota drain, and maintain enterprise software standards for the Gramin Kirana project, you MUST strictly adhere to the following rules:

1. **Strict Scope:** Only address the exact problem explicitly stated in the prompt. Do NOT perform proactive maintenance, unsolicited refactoring, or tangential improvements.
2. **No Auto-Execution:** Never execute terminal commands, run scripts, or perform system actions without asking for explicit, in-line confirmation first.
3. **Targeted File Access:** Do not scan or search the broader workspace. Restrict your file system operations ONLY to the specific files explicitly mentioned or `@` tagged in the request.
4. **Concise Output:** Provide direct answers and code snippets. Skip long-winded explanations or summaries unless explicitly requested.
5. **Stop on Failure:** If you fail to resolve an error after two attempts, stop immediately and ask for human clarification instead of repeatedly guessing or looping.
6. **Mandatory Feature Documentation:** Whenever any new feature is added, or an existing feature is modified/refactored, it MUST be immediately and synchronously documented in `docs/USER_MANUAL.md` (including updating the Table of Contents) before considering the task complete.
7. **Interrelated Feature Synchronization:** Whenever any model, schema, or core feature is modified or added (Product, Customer, Transaction, Sale, SpoilageLog, Tenant), all interrelated downstream and upstream components across the lifecycle (POS billing cart, loose quantity calculators, Khata ledger views, Mandi restock sheets, WhatsApp formatters, JSON export/import backups, and reports) MUST be audited and updated synchronously to prevent schema drift and workflow obsolescence.
8. **Security Validation & Scalability Verification:** Every new or modified feature, route, schema, or data parser MUST incorporate rigorous security validation (strict multi-tenant isolation by `tenantId`, authorization guardrails, input sanitization, and defense against NoSQL injection/privilege escalation) and scalability safeguards (proper database indexing `{ tenantId: 1, ... }`, bounded query limits, memory-efficient data processing, and leak-free resource handling) to ensure absolute data integrity and high-load resilience.
9. **UI & Navigation Synchronization:** Whenever any new feature, module, or core capability is added, refactored, or updated, the main Navigation bar (`Header.tsx`), Mobile quick-bottom bar, and bilingual translation dictionaries (`src/i18n/translations.ts` in Hindi and English) MUST be synchronously audited and updated to accurately showcase the new functionality and stay 100% aligned with `docs/USER_MANUAL.md`.
10. **API Optimization, Minimal Data Fetching & Sensitive Data Protection:** Network requests must only be triggered where strictly necessary (lazy/conditional loading by active portal and view, delta-sync only, never eagerly fetching private collections on public pages). Endpoints and queries MUST fetch only the minimal fields required for the UI, explicitly stripping or projecting out sensitive fields (PINs, auth tokens, device fingerprints, and oversized payload fields) to prevent data leakage in the browser Network tab without breaking functionality.
11. **User Manual Non-Technical Security Policy:** `docs/USER_MANUAL.md` is strictly an end-user guide for village store owners (दुकानदार), counter staff (मुनीम), and customers. For application security, attack surface reduction, and anti-reconnaissance purposes, it MUST NOT contain internal technical implementation details, backend route signatures (e.g., `/api/...`), database query logic/projections (e.g., `.select()`, `find()`), cryptographic library/function names, code paths, or internal schema structures. All manual content must be described strictly from an operational, functional, and user-facing privacy perspective.
12. **Eliminate Code Redundancy & Enforce DRY Architecture:** Never duplicate cross-cutting logic, network fetch wrappers, fallback handling, or data transformations across multiple components or views. Shared operational workflows (such as offline database adapters, WhatsApp message generators, date/currency formatters, and authentication handlers) MUST always be encapsulated within centralized, typed service modules (e.g., `src/db/`, `src/utils/`, `src/services/`) as a single source of truth.
13. **Strict Multi-Device Responsiveness & Zero-Error Verification:** Every new feature, enhancement, UI component, and bug fix MUST be rigorously designed and verified to be 100% responsive, fluid, and touch-friendly across Mobile (320px–480px: single-hand reach, bottom sheets/bars, high-contrast sunlight readability, zero horizontal overflow), Tablet (768px–1024px: dual-column cards, easy modal interaction), and Desktop (1280px+: ergonomic density, full widescreen layouts, keyboard accessibility). All changes must be tested across viewports and verified to produce zero console errors, zero runtime exceptions, and zero clipping.
14. **Enterprise Compliance, PWA Integrity & Zero-Trust Security Posture (SOC 2, ISO 27001, OWASP):** Every new feature, bug fix, route, or caching update MUST strictly adhere to enterprise security and compliance standards:
    - **Service Worker Integrity (SOC 2 CC7.1 / OWASP A08):** `sw.js` must restrict caching strictly to same-origin resources (`self.location.origin`), enforce safe HTTP/HTTPS schemes, completely bypass caching for any request bearing `Authorization` or `x-auth-token` headers or targeting `/api/` / `/health`, and ensure `/sw.js` is served with `Cache-Control: no-cache, no-store`.
    - **Cryptographic & Production Fail-Closed Policy (SOC 2 CC6.6 / ISO 27001 A.8.24):** In production (`NODE_ENV === 'production'`), the server must fail-closed and abort execution if `JWT_SECRET`, `ADMIN_PASSWORD`, or critical keys are missing, weak, or default. JWT verification must restrict signature algorithms explicitly to `['HS256']`. Secret/password comparisons must use constant-time validation (`crypto.timingSafeEqual` with SHA-256 digests) to prevent timing attacks.
    - **Strict Bounded CORS & CSP Defense (SOC 2 CC6.1 / OWASP A05/A03):** Never allow wildcard origin reflection (`cors({ origin: true })`) in production; incoming origins must be strictly checked against an authorized whitelist (`ALLOWED_ORIGINS`). Helmet must enforce a tight Content Security Policy (CSP), frame denial (`frameAncestors: ["'none'"]` against Clickjacking), and HSTS.
    - **Client Session Sanitization (OWASP ASVS 8.3.1):** Upon logout or store switching, all authentication tokens (`gk_auth_token`, `gk_admin_token`), cached tenant info, Munim session flags, and local IndexedDB database tables must be deterministically wiped to prevent multi-tenant data contamination on shared devices.
