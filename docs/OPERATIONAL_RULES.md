# Antigravity AI Operational Rules (Original Reference)

You are operating within a constrained compute environment. To optimize resource usage and prevent quota drain, you MUST strictly adhere to the following rules:

1. **Strict Scope:** Only address the exact problem explicitly stated in the prompt. Do NOT perform proactive maintenance, refactoring, or tangential improvements.
2. **No Auto-Execution:** Never execute terminal commands, run scripts, or perform system actions without asking for explicit, in-line confirmation first.
3. **Targeted File Access:** Do not scan or search the broader workspace. Restrict your file system operations ONLY to the specific files explicitly mentioned or `@` tagged in the request.
4. **Concise Output:** Provide direct answers and code snippets. Skip long-winded explanations or summaries unless explicitly requested.
5. **Stop on Failure:** If you fail to resolve an error after two attempts, stop immediately and ask for human clarification instead of repeatedly guessing or looping.
6. **Mandatory Feature Documentation:** Whenever any new feature is added, or an existing feature is modified/refactored, it MUST be immediately and synchronously documented in `docs/USER_MANUAL.md` (including updating the Table of Contents) before considering the task complete.
7. **Interrelated Feature Synchronization:** Whenever any model, schema, or core feature is modified or added, all interrelated downstream and upstream components across the lifecycle (including sample CSV import templates, parsers, export utilities, filters, UI modals, and reports) MUST be audited and updated synchronously to prevent schema drift and workflow obsolescence.
8. **Security Validation & Scalability Verification:** Every new or modified feature, route, schema, or data parser MUST incorporate rigorous security validation (strict multi-tenant isolation, authorization guardrails, input sanitization, and defense against NoSQL injection/privilege escalation) and scalability safeguards (proper database indexing, bounded query limits, memory-efficient data processing, and leak-free resource handling) to ensure absolute data integrity and high-load resilience.
9. **Public Homepage & Showcase Synchronization:** Whenever any new feature, module, or core capability is added, refactored, or updated, the public homepage (including `Hero` stats, `ERPModulesSection` pillars, `AboutSection`, and navigation links) MUST be synchronously audited and updated to accurately showcase the new functionality and stay 100% aligned with `docs/USER_MANUAL.md`.
10. **API Optimization, Minimal Data Fetching & Sensitive Data Protection:** Network requests must only be triggered where strictly necessary (lazy/conditional loading by active portal and view, never eagerly fetching private collections on public pages). Endpoints and queries MUST fetch only the minimal fields required for the UI, explicitly stripping or projecting out sensitive fields (passcodes, PINs, auth tokens, and oversized payload fields) to prevent data leakage in the browser Network tab without breaking functionality.
11. **User Manual Non-Technical Security Policy:** `docs/USER_MANUAL.md` is strictly an end-user guide for school administrators, teachers, parents, and staff. For application security, attack surface reduction, and anti-reconnaissance purposes, it MUST NOT contain internal technical implementation details, backend route signatures (e.g., `/api/...`), database query logic/projections (e.g., `.select()`, `find()`), cryptographic library/function names, code paths, or internal schema structures. All manual content must be described strictly from an operational, functional, and user-facing privacy perspective.
12. **Eliminate Code Redundancy & Enforce DRY Architecture:** Never duplicate cross-cutting logic, network fetch wrappers, fallback handling, or data transformations across multiple components or views. Shared operational workflows (such as AI proxying, API communication, authentication headers, and data parsing) MUST always be encapsulated within centralized, typed service modules (e.g., `src/services/...`, `src/utils/...`) as a single source of truth.
13. **Strict Multi-Device Responsiveness & Zero-Error Verification:** Every new feature, enhancement, UI component, and bug fix MUST be rigorously designed and verified to be 100% responsive, fluid, and touch-friendly across Mobile (320px–480px: single-hand reach, bottom sheets/bars, high-contrast sunlight readability, zero horizontal overflow), Tablet (768px–1024px: dual-column cards, easy modal interaction), and Desktop (1280px+: ergonomic density, full widescreen layouts, keyboard accessibility). All changes must be tested across viewports and verified to produce zero console errors, zero runtime exceptions, and zero clipping.
